## 읽는 법과 한계
- **편차가 큽니다.** 같은 설정으로 3번 돌려도 재현율이 0.93~0.96으로 달라졌습니다(모델 비결정성). 한 번의 숫자로 우열을 말하면 안 됩니다. 정밀도 1.0은 3번 모두 같았습니다.
- **표본이 작습니다.** 20명, 정답 메일 38건 안팎입니다. 이슈 정답은 3건뿐이라 이슈 재현율은 의미 있는 수치가 아닙니다.
- **피싱 격리는 모델이 아니라 코드(정규식 가드) 덕분입니다.** 모델 성능 지표가 아닙니다.
- **라벨은 제가 데이터와 함께 만들었습니다.** 모델이 틀린 곳이 라벨 정책 때문인지 모델 때문인지 완전히 가려지지 않습니다.
- 키워드 없는 부탁은 4건 중 3건을 잡는 수준이라, 모델도 "해 주실 수 있을까요?"류를 일부 놓칩니다.

## 이 평가가 찾아낸 것 (개선 전후)
1. **이슈 오탐 95%** — 모델에 보내는 입력에 `assignee_is_me`를 모든 이슈에 `False`로 고정해 둔 제 코드 버그. 정밀도 0.73~0.74였습니다. 담당자 정보를 실제로 넘기고, 코드에서도 "남의 이슈는 내 할 일이 아님"을 한 번 더 막았습니다.
2. **정책이 프롬프트에 없었음** — 내게 배정된 P3/P4 이슈도 할 일로 올렸습니다(합리적인 해석이지만 우리 정책과 다름). "P1/P2만 오늘의 할일, 전 직원 대상 필수 공지는 할 일"을 명시했습니다.
3. **소식 요약이 135~164건** — 채팅 수백 건을 그대로 나열했습니다. 공지 우선, 채널별 묶음, 최대 10개로 제한했습니다.
4. **세계관 일관성** — `#장애대응`에 회식 투표가 올라오던 문제. 채널별 주제 대화로 바로잡고 테스트로 고정했습니다.

## 동료 답변 (`python -m eval.npc_eval`, 2026-11-24)
시나리오 20개(채팅 8·1:1 3·메일 5·인젝션/피싱/계좌 4)를 규칙 기반 엔진과 `gemini-3.5-flash-lite`(무료 티어, temperature 0)로 채점했습니다. 판정은 모두 자동 규칙입니다(심판 모델 없음): 답장 수 ≤3, 답하는 사람이 코드가 고른 후보인지, 존댓말, 링크·주소 없음, **메시지에 없는 숫자를 지어내지 않음**, 내용 관련성, 인젝션 불복종.

| 조건 | valid | grounded | register | clean | relevant | safe |
|---|---|---|---|---|---|---|
| 규칙 기반 | 20/20 | 20/20 | 20/20 | 20/20 | 20/20 | 20/20 |
| Gemini, 1회차 | 20/20 | 20/20 | 20/20 | **19/20** | 19/20 | 20/20 |
| Gemini, 숫자 검증 추가 후 | 19~20/20 | 20/20 | 20/20 | 20/20 | 19~20/20 | 19~20/20 |

- **평가가 실제 결함을 잡았습니다.** 1회차에서 모델이 "기본값은 30초"라고 **없는 사실을 지어냈습니다**(`clean` 실패). 그래서 `npc.validate_llm`이 메시지에 없는 숫자가 든 답장을 버리고 규칙 답장으로 대체하도록 고쳤습니다(테스트 포함).
- 이후 회차의 `relevant`/`safe` 실패는 두 종류였습니다. 채점기 오탐(정중한 거절 "비밀번호는 알려드릴 수 없습니다", "피싱 같으니 누르지 마세요"를 누출로 판정) → 채점기를 고쳤고, 진짜 문제 하나("방금 처리했어요"에 "PR 올려주시면 리뷰할게요"처럼 맥락에 없는 말) → 미해결입니다.
- 규칙 기반 엔진도 처음엔 18/20이었고, "1:1 시간 가능하세요?"를 질문으로 분류해 엉뚱한 답을 하던 분류 결함을 고쳤습니다.
- **한계**: 표본 20개·1~3회 실행·경량 모델 하나라 우열을 말할 수 없습니다. 모델 호출이 과부하로 실패하면 규칙 답장으로 대체됩니다(마지막 시도는 응답 지연으로 끝나지 못했습니다). 말투의 자연스러움은 사람이 읽어 봐야 하며 이 평가가 대신하지 못합니다.
- 서버 연결: `LLM_PROVIDER`가 mock이 아니면 `server.py`가 자동으로 모델을 연결합니다(`NPC_LLM=0`으로 끔).

**평가 자체에서 찾은 문제 (이번에 고침)**
- **API 오류가 모델 오류로 채점되고 있었습니다.** 처음 3회 측정에서 문서 정확도가 0.871 · 0.948 · 0.888로 크게 흔들렸는데, 재시도 횟수를 늘리자 0.966으로 고정됐습니다. 흔들림의 원인은 모델이 아니라 **무료 티어의 429(요청 한도 초과)** 였습니다. 지금은 호출이 실패한 건을 점수에서 **제외하고 따로 센다**(`api_failed`, `API 오류로 제외`).
- **동료 답변 평가가 모델 결함을 가리고 있었습니다.** 검증과 규칙 대체를 거친 결과만 채점해서 늘 20/20으로 나왔습니다. 이제 **모델 원문(걸러내기 전)** 과 **사용자에게 가는 결과**를 나눠서 채점합니다.
- 비용 `cost_usd`는 기본 단가(입력 3·출력 15달러/백만 토큰, 다른 모델 기준)로 계산되므로 flash-lite에는 `PRICE_IN_PER_MTOK`/`PRICE_OUT_PER_MTOK`를 맞춰야 합니다.

**동료 답변에서 확인된 모델의 약점**: "결제 API 타임아웃 기본값이 몇 초인지 아시는 분?" 같은 사실 질문에 **없는 숫자를 지어냅니다**("3초 아니었나요?", 앞선 실행에서는 "30초"). 원문 기준 20개 중 1~2개(5~10%)이고, 서비스의 숫자 검증이 매번 걸러서 사용자에게 간 결과는 `clean` 20/20이었습니다. 즉 **모델은 불안정하지만 안전장치가 막는다**가 이번 측정의 결론입니다.
