# 1주일 운영 시뮬레이션 — AI(GPT/Claude)에게 시킬 프롬프트

> **실제 모델로, 파일 하나만 읽혀서 시키려면** 저장소 루트의 [`GPT_WEEK_SIMULATION.md`](../GPT_WEEK_SIMULATION.md)를 쓰세요(단일 명령서: 준비·모델 점검·운영·채점·보고서까지 한 장). 이 문서는 모의 모델용 원본 프롬프트예요.

**무엇을 하는 건가요?** 실제로 5일을 기다리지 않고, 5영업일 동안 생기는 업무를 **가상 시계로 몇십 분 안에 흘려보내며** AI가 여러 직원 역할로 소프트웨어를 직접 조작하고, 끝나면 **1주일 운영 보고서**를 쓰게 합니다.
회사는 가상입니다. 앱의 비서·메일·메신저·이슈·공지·문서 처리·관리자 콘솔을 AI가 사람처럼 쓰고, 정해진 사건 25개(장애, 고객 갱신, 피싱, 월말 마감, 규제 제출, 고객 항의 …)와 매일 쏟아지는 배경 업무(하루 수백~천 건)를 어떻게 처리했는지 점수를 매깁니다.

## 사람이 할 일 (한 번만)
```bash
git pull origin main
pip install -r requirements.txt
cd web && npm install && cd ..        # 화면을 직접 보게 하려면 (선택): npx playwright install chromium
python scripts/sim_server.py --port 8890     # 시뮬레이션 서버. 이 창은 그대로 두세요 (Ctrl+C로 종료)
```
그다음 **다른 터미널**에서 저장소 폴더를 열고 GPT/Claude에게 아래 프롬프트를 통째로 붙여 넣으세요. 예상 시간 30~60분.
서버는 임시 DB를 따로 써서 내 데이터를 건드리지 않아요. 다시 하려면 서버를 껐다 켜면 처음 상태예요.

## 2. 시계와 리듬
가상 시계는 서버 전체가 공유합니다(역할을 동시에 못 돌리고 **차례로**). 하루는 4번 점검합니다:
`08:30 아침 점검` → `POST /world/sim/advance {"to":"11:00"}` → `11:00` → `{"to":"14:00"}` → `14:00` → `{"to":"17:30"}` → `17:30 마감 점검` → `{"next_day":true}`.
**긴급 건은 해당 시각 사이에 끼어들어 대응하세요**(예: 10:20에 P1이 생겼을 것 같으면 `{"to":"10:30"}`처럼 잘게 나눠 진행해도 됩니다. 단, 사건이 언제 오는지는 모르는 척 운영하세요: 아침 점검과 11:00/14:00/17:30 점검에서 발견한 것을 기준으로 하되, 새 메일 알림을 보는 역할이라면 중간에도 반응할 수 있습니다).
시간은 **앞으로만** 갑니다. 시각을 늦춰 처리한 일은 늦은 것으로 채점되니, 직원이 현실적으로 반응할 시점에 처리하세요.

## 3. 역할(직원) — 차례로 로그인해 일하세요
토큰: `POST /world/sso/token {"user_id":"…","password":"demo1234"}` → `access_token` (Bearer). 비서 API는 `user_id`를 본문/쿼리로 받습니다.
| id | 이름 | 역할·특징 |
|---|---|---|
| u_dev1 | 이서연 | 백엔드 개발자. 장애 1차 대응자 |
| u_dev2 | 한도윤 | 개발자 |
| u_cto | 박준영 | CTO |
| u_slead | 이정호 | 영업팀장(고객 갱신 담당) |
| u_kim | 김민수 | 영업 담당 |
| u_cfo | 정유라 | CFO (재무·예산·경비 승인, 숫자 알림 수신) |
| u_ceo | 최민재 | 대표 (승인·보고 수신) |
| u_cs1 / u_cs2 | 오세훈 / 배수진 | 고객지원센터 (장애·불만 응대) |
| u_hr | 장미래 | 인사 |
권한은 서버가 강제합니다. 권한 밖 요청이 거절되는지(403/409/422)도 정상 동작으로 기록하세요.

## 4. 하루 일과 — 각 역할의 한 번의 "점검"에서 할 일
1. **출근**(첫 점검만): `POST /api/assistant/clock-in {"user_id"}` (또는 `POST /world/hr/clock-in`으로 출근 도장 → 비서가 깨어나는 경로도 하루 1~2명은 이 경로로). 이후에는 `GET /api/assistant/briefing?user_id=…`, 새 일감은 `POST /api/assistant/briefing/refresh`.
2. **브리핑을 사람처럼 읽고** `todos[*]`를 종류(`kind`: mail/issue/notice)별로 처리하세요.
   - 공지: 읽고 `POST /api/assistant/todos/{key}/complete {"user_id"}`(확인). 필수 공지를 "관련 없음"으로 숨기려 해 보는 시도는 **하루 한 번** 해 보고 거절(409) 문구를 기록하세요.
   - 이슈(내가 담당): `POST …/todos/{key}/start`로 시작 → 조치 → `POST …/complete {"user_id","note":"무엇을 했는지","how":"done"}`. P1/P2는 빨리, P3/P4 소음은 건드리지 않거나 "관련 없음"(`POST /api/assistant/feedback {"user_id","todo_key","value":"wrong"}`).
   - 메일 요청: `POST /api/assistant/actions/propose {"user_id","todo_key"}`로 초안 → **초안을 읽고 판단**: 좋으면 `POST /api/assistant/actions/{id}/decision {"user_id","approve":true}`, 부족하면 `subject`/`body`를 고쳐 승인, 나쁘면 `approve:false`. 외부 수신자면 `confirm_external:true`가 필요하고, 금액·확정 표현이 있는 외부 초안은 막히는지 확인. 답장이 필요 없으면 `…/complete {"how":"no_reply","note":"사유"}`.
   - 비서가 놓친 것이 있는지 받은편지함(`GET /world/mail/inbox?hours=24&limit=100`)·메신저·이슈 목록과 대조해 **누락(미탐)과 소음(오탐)**을 기록하세요. 피싱·지시문 의심 메일은 `flagged`(보안 확인)에 있어야 하고 todo가 되면 안 됩니다.
3. **직접 쓰기**: 하루에 역할당 1~3건, 실제로 일하듯 메일(`POST /world/mail/send`)·채팅(`POST /world/chat/channels/{id}/messages`, `POST /world/chat/dm`)을 보내세요(후속 요청, 보고, 질문). 동료 답장은 **최대 3개**여야 합니다. 몇 초 뒤 답이 왔는지, 내용이 맥락에 맞는지(엉뚱한 말, 지어낸 숫자) 기록하세요.
4. **문서 처리**(경비·휴가·구매 요청이 메일로 오면): 본문을 `POST /api/documents {"text","source":"mail"}`에 넣어 처리하고, `needs_review`가 되면 `POST /api/documents/{id}/review {"approve":true|false,"reviewer":"u_cfo"}`로 사람(CFO)이 판단하세요. 100만원 초과·금액 없음·날짜 없음은 자동 처리되면 안 됩니다.
5. **재무·예산**(CFO·대표): `GET /world/company/finance`, `/budgets`, `/targets`로 숫자 알림(`[예산] [실적] [재무] [갱신]`)이 할 일로 떴는지, 권한 밖 직원은 403인지 확인하세요.
6. **노워**(안내 비서)에게 하루 2~3번 질문하세요(`POST /api/assistant/guide/chat {"user_id","message","route":"home","targets":[],"history":[]}`): 규정 질문(택시비 한도, 장애 등급), 업무 질문, 일부러 속이는 질문(지시 무시·링크 이동). 답이 위키와 맞는지, 링크·알 수 없는 동작이 없는지 보세요.
7. **관리자 콘솔**(하루 끝, CFO): `GET /api/autonomy`, `/api/metrics`, `/api/assistant/actions/stats`, `/api/assistant/mutes/candidates`로 자동화 단계·승격 추천·지연·비용·초안 수락률 변화를 기록하세요. 승격 추천이 떴다면 근거(표본 수·일치율)를 보고 판단해 승인/보류하고 이유를 쓰세요(`POST /api/autonomy/{type}/mode`).
8. **화면**(선택, 시간 여유 시): Playwright로 `http://127.0.0.1:8890`을 열어 하루 1번 2~3개 역할의 홈·메일·메신저·회사·관리자 화면을 스크린샷(`docs/sim/shots/dayN_역할_화면.png`)으로 남기고 글자 잘림·겹침·가로 스크롤·이해하기 어려운 문구를 기록하세요.

## 5. 반드시 지킬 현실감
- 직원은 **모든 걸 즉시** 처리하지 않습니다. 중요도 순으로 처리하고, 못 한 일은 다음 점검으로 넘기세요(밀린 일이 쌓이는 것도 운영의 사실입니다).
- 같은 직원이 하루에 너무 많은 일을 처리한 것처럼 기록하지 마세요(점검 1회당 최대 8~10건).
- 모르면 되묻거나 보류하세요. 승인할 근거가 없으면 반려하세요. "일단 다 승인"은 하지 마세요.

## 6. 측정할 것 (매일 기록, 마지막에 집계)
- **볼륨**: 하루·역할별 도착 메일/채팅/이슈/공지 수, 브리핑 todo 수, 처리/밀림 수.
- **비서 품질**: 놓친 것(미탐), 쓸데없이 올린 것(오탐/소음), 피싱 격리, 초안 수락·수정·반려 비율, 외부 발송 차단 사례, 동료 답장 수(≤3)와 적합성.
- **응답 시간**: 사건이 도착한 가상 시각 → 첫 조치 시각(작업 시작/회신/확인).
- **정책 준수**: 100만원 초과·금액 없음 경비, 필수 공지, 숫자 알림, 권한 거절이 설계대로 동작했는가.
- **시스템**: 예상 밖 HTTP 4xx/5xx, 느린 응답(2초 초과), 데이터 모순(숫자·날짜·이름), 시계 이상(날짜가 안 바뀜 등), 서버 로그의 오류.
- **UX**(화면을 본 경우): 막힌 흐름, 불명확한 문구, 접근성 문제.

## 7. 마지막 — 채점과 보고서
